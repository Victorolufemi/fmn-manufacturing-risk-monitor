## 1. Business objective

> "Machines go down without warning and it costs us hours of production. I want to know ahead of time which machines are at risk, and why - not just a red light with no explanation."

That translates into three requirements, all of which shape the model:

1. **Ahead of time.** A warning is only useful if maintenance can act on it, so lead time is a first-class metric, not an afterthought.
2. **Which machines.** The output must rank the fleet, not just classify hours, so the model is evaluated per failure episode as well as per row.
3. **And why.** Every score is accompanied by model-derived drivers and the sensor evidence behind them.

## 2. Prediction target

`failure_within_horizon` = 1 if a `failure_event` occurs in the window **(t, t+72h]**
for that machine, and 0 otherwise.

The window excludes t itself, so a row can never be labelled positive by its own failure flag. Two categories of row are removed from training and evaluation entirely:

- **The failure hour itself.** At that instant the machine is already down. That is an observation, not a prediction.
- **Hours preceding preventive maintenance.** The data contains 5 run-hours resets with no failure flag, on machines showing sustained vibration around 2.2 SD above their own normal. We cannot know whether those machines would have failed, so those hours are **censored**. Labelling them negative would teach the model that rising vibration is harmless - the exact opposite of what the sponsor needs.

## 3. Prediction horizon

**Chosen: 72 hours.**

Among horizons that catch every failure episode in rolling-origin CV while staying under 0.05 false alerts per machine-day, this horizon has the highest prevalence-normalised PR-AUC lift. Raw PR-AUC rises mechanically with the horizon because the positive rate rises, so it cannot be used to compare horizons. The choice is also physically supported: the degradation ramp in this dataset begins 70-170 hours before failure, and this horizon gives maintenance planners several shifts of warning without leaving machines parked in an alerted state for the better part of a week.

**Why not raw PR-AUC.** PR-AUC is bounded below by the positive rate, and the positive rate rises mechanically with the horizon, so a longer horizon scores higher without being better. PR-AUC *lift* (PR-AUC divided by the positive rate) is comparable across horizons and is what the selection rule uses, under two hard operational constraints: catch every failure episode, and stay at or below 0.05 false alerts per machine-day.

**Why this is physically supportable.** The data profile shows both sensors already clearly elevated 72 hours before failure (temperature ~3.2 SD, vibration ~2.6 SD above each machine's own normal), with degradation beginning 70-170 hours out. A 72-hour horizon sits inside the real degradation ramp rather than assuming one.

**What it means operationally.** 72 hours is three shifts of warning - enough to order a part and schedule the work into a planned window instead of reacting to a line stoppage.

## 4. Features

47 features, all computed strictly from observations at or before the prediction timestamp for that machine only.

| Group | What it captures | Examples |
|---|---|---|
| Current readings | Where the machine is now | `temperature_c`, `vibration_mm_s` |
| Machine-relative | How far from **this machine's own** normal | `temp_z_vs_baseline`, `vib_dev_from_baseline`, `vib_ratio_to_baseline` |
| Rolling statistics | Level and instability over 6h / 24h / 72h | `vib_roll_std_24h`, `temp_roll_mean_72h`, `vib_roll_max_24h` |
| Change and trend | Direction and steepness | `temp_change_24h`, `vib_slope_24h`, `temp_accel`, `vib_short_vs_long` |
| Maintenance history | Time-based wear signal | `run_hours_since_maintenance`, `hours_since_last_failure`, `prior_failure_count` |
| Temporal | Shift and weekday patterns | `hour_sin`, `hour_cos`, `day_of_week` |
| Data quality | Whether a reading was imputed | `temp_imputed`, `vib_imputed` |

### Machine-specific baselines

Machines run at genuinely different operating points - median temperature spans 56.3 to 69.9 degC and median vibration spans 0.31 to 1.25 mm/s across the fleet. A global rule such as "temperature above 70 degC means risk" would fire constantly on the hot machines and never on the cool ones.

Each machine therefore carries its own trailing baseline:

```
baseline(t) = expanding median of that machine's readings up to t - 24h
```

The 24-hour lag matters: without it, an in-progress degradation ramp would inflate the machine's own notion of normal and mask itself. This is verified directly in `tests/test_features.py::test_baseline_excludes_the_most_recent_24h`.

Machines with under 96 hours of usable history fall back to a **production-line pooled baseline** fitted on established machines in the training window only. That is the cold-start path, and it is recorded per row so the UI can disclose it.

## 5. Guarding against leakage

Four specific hazards existed in this dataset, and each is handled:

| Hazard | Why it would leak | Mitigation |
|---|---|---|
| `run_hours_since_maintenance` resets to exactly 0 at every failure hour | A model could read `run_hours == 0` as "a failure just happened" | The failure hour is excluded from training and evaluation; run-hours at any other t is legitimately known in advance |
| Rolling and baseline statistics | A centred or full-sample window would see the future | All windows are trailing; the baseline is an expanding median lagged 24h |
| Failure-history features | Counting the current failure would be circular | `hours_since_last_failure` and `prior_failure_count` refer only to strictly earlier failures |
| Pooled baselines fitted on all data | The test period would influence training-period features | The baseline book is fitted on the development window only |

The decisive check is `tests/test_features.py::test_no_future_leakage`, which rebuilds every feature from a truncated history and asserts the past values are numerically identical. If any feature peeked forward, that test would fail.

## 6. Validation design

Rows are hourly and heavily autocorrelated, so a random train/test split would put a machine's 14:00 reading in training and its 15:00 reading in test and report near-perfect, meaningless scores. Validation is strictly chronological.

```
Development period   2026-01-01 .. 2026-04-06   33,881 rows, 10 failure episodes
  rolling-origin CV, 3 expanding folds:
    fold 1: train < 2026-02-15   validate 2026-02-15 .. 2026-03-05
    fold 2: train < 2026-03-05   validate 2026-03-05 .. 2026-03-20
    fold 3: train < 2026-03-20   validate 2026-03-20 .. 2026-04-06

Test period          2026-04-06 .. 2026-04-30   9,137 rows, 7 failure episodes
  touched exactly once, scored by a model fitted only on the development period
```

The pooled out-of-fold predictions from the CV are used for three things and three only: choosing the horizon, choosing the model, and fitting the calibrator and threshold. The test period is never involved in any of those decisions.

## 7. Class imbalance

17 failure events in 43,344 rows is a 0.039% hourly event rate. At the 72-hour horizon that becomes 725 positive rows out of 33,881 in development (2.14%).

**The number that actually constrains the work is 17, not 43,344.** Positive rows are almost perfectly autocorrelated within an episode, so the effective sample size is the count of failure episodes. Every decision follows from that:

- **Accuracy is banned as a headline metric.** Predicting "no failure" always would be over 97% accurate and completely worthless.
- **Episode-level metrics sit alongside row-level ones**, because a model that catches one long episode can beat one that catches three short ones on row metrics while being worse for the plant.
- **Class weighting was tested, not assumed.** Both a weighted and an unweighted gradient-boosting model were compared on identical folds; the table in section 8 shows which won.
- **Threshold tuning does the balancing work** instead of resampling, which with 17 episodes would mostly manufacture duplicates.

## 9. Calibration

The raw classifier separates well but is not calibrated; at the tuned operating point an alarming machine scored around 0.03, which is meaningless on a plant floor. Isotonic calibration is monotone, so PR-AUC and ROC-AUC are unchanged - only the numbers shown to people move.

Method: **isotonic regression on pooled out-of-fold predictions**. At the tuned operating point the raw classifier score was 0.007; after calibration the same decision boundary sits at 0.103, which is a number a supervisor can reason about.

Calibration is monotone, so it changes no ranking metric - PR-AUC and ROC-AUC are identical before and after. This is asserted in `tests/test_model_and_risk.py::test_calibration_does_not_change_ranking_metrics`.

## 10. Operating threshold and risk bands

**Operating threshold: 0.103**

Maximises F2 on pooled out-of-fold predictions from the rolling-origin CV. F2 weights recall twice as heavily as precision because an unplanned stoppage costs hours of lost production while a false alert costs one inspection.

At that threshold, on pooled out-of-fold predictions:

- Precision **0.75**
- Recall **0.97**
- F1 0.85, F2 0.92

### The business trade-off, stated explicitly

A **false negative** is a machine that fails without warning: hours of unplanned downtime, lost production, possible damage to the asset and to in-process product.

A **false positive** is an inspection that finds nothing: one technician, part of one shift.

These are not close to equal, which is why the threshold maximises F2 (recall weighted twice as heavily as precision) rather than F1, and why the horizon rule requires 100% episode detection rather than merely good average performance.

### Risk bands

| Band | Score range | How it was set | What the plant team should do |
|---|---|---|---|
| **CRITICAL** | >= 0.701 | Lowest threshold at or above HIGH with out-of-fold precision >= 0.90. | Investigate now |
| **HIGH** | 0.103 - 0.701 | F2-optimal operating threshold - act on this shift. | Schedule an inspection this shift |
| **MEDIUM** | 0.073 - 0.103 | Watch list: highest threshold below HIGH that still recovers >= 98% of at-risk hours. | Watch list; no call-out |
| **LOW** | < 0.073 | No elevated risk signal. | Normal operation |

The bands are derived from the tuned threshold rather than picked as round numbers, so HIGH always means exactly "at or above the operating point".

### How to read these numbers honestly

The scores are high, and the reason is a property of the data rather than of the modelling: the degradation signature here is clean and close to monotone, with both sensors rising several standard deviations above baseline over several days before every failure. Real plant data is noisier, sensors drift and fail, and failure modes exist that these two sensors cannot see at all. **These figures should be read as evidence that the pipeline is correct and leak-free, not as a forecast of production performance.** The genuine limits are in section 14.

These are **grouped** permutation importances. Per-feature permutation is misleading here because the features are correlated by construction - permuting `vib_roll_mean_6h` alone barely moves the score while `vib_roll_mean_24h` carries the same information. Permuting whole families answers the question an engineer is actually asking.

One result is worth flagging to the business: **maintenance history and run-hours contribute almost nothing.** Failures in this dataset occurred anywhere from 15 to 2,860 run-hours after maintenance. Time-based servicing would not have predicted them; condition monitoring does. That is a direct argument for the tool.

### Why is *this* machine flagged right now

Per-machine drivers are computed by **counterfactual re-scoring**: each feature family is set back to that machine's own typical values and the fitted model is run again. The drop in risk is that family's contribution.

This is a real evaluation of the deployed model, not a heuristic, and it translates directly into plain English - the UI can say "at normal vibration variability this machine would score 39% instead of 99%" rather than naming a feature and leaving the reader to guess.

### Plain-English explanation

The backend assembles a structured evidence object of real measurements and calls Claude at request time to narrate it. The prompt forbids using anything outside that evidence, requires observed readings to be distinguished from model predictions, forbids claiming certainty, and requires limited history to be disclosed. The same evidence object is returned to the browser and rendered under the explanation, so every number the AI quotes can be checked on screen.

If the AI service is unavailable the endpoint returns an evidence-only summary, clearly labelled as such. The tool never goes dark and never presents a fallback as an AI answer.

## 13. Cold start - newly commissioned machines

MCH-300, MCH-301 have 72 hours of history each, against 2,880 for every other machine, and neither has ever failed.

**Strategy:** Pooled (fleet-wide) model with production-line baselines. New machines have no failure history of their own, so a per-machine model is impossible; the pooled model transfers the fleet degradation signature, and the machine-relative features fall back to a line-level baseline until 96 hours of history exist. Long-window features (72h rolling, 24h change) are also partly unavailable, which the model tolerates natively via NaN handling. Scores for these machines carry an explicit limited-history warning in the API and UI and are never presented with the same confidence as established machines.

Concretely:

- A **pooled fleet-wide model** is used rather than per-machine models. With 17 failures across 15 machines, per-machine models are impossible even for established assets.
- Machine-relative features fall back to a **production-line baseline** learned from established machines on the same line, and the substitution is recorded per row in `baseline_source`.
- Long-window features (72h rolling, 24h change) are partly unavailable. The gradient-boosting model handles the resulting NaNs natively rather than having them silently imputed to a misleading value.
- The API returns an explicit `cold_start` block, and the UI shows a **Limited history** warning on the machine page and a **New** tag in the fleet table.

**The honest limitation:** Neither newly commissioned machine has experienced a failure, so there is no held-out evidence about accuracy on machines with this little history. The honest statement is that their scores are unvalidated, not that they are accurate.

No confidence percentage is shown for these machines, because none has been measured. Inventing one would be worse than saying nothing.

## 14. Limitations

1. **17 failure events.** Every metric here rests on 17 episodes, 7 of them in the test period. Confidence intervals on any of these numbers are wide, and a single differently-behaving failure would move them visibly.
2. **One plant, 120 days, one season.** No evidence about summer/winter ambient effects, product changeovers, or shutdown periods.
3. **Two sensors.** Failure modes that do not raise temperature or vibration - electrical faults, control failures, tooling breakage - are invisible to this model. A LOW score means "no signal in these two sensors", not "this machine is healthy".
4. **Cold-start machines are unvalidated**, as set out in section 13.
5. **Clean degradation signature.** The high scores reflect a dataset where degradation is close to monotone. Expect materially lower performance on raw plant data with sensor drift and outages.
6. **The model does not know about maintenance quality.** It sees that run-hours reset, not what was done. MCH-214 failed 15 hours after a maintenance event, which the data cannot explain.
7. **Static extract.** The prototype scores a fixed historical dataset. A production deployment needs streaming ingestion, drift monitoring, and periodic retraining, none of which is built here.

## 15. What would improve it

1. **More failure history.** The binding constraint is event count, not row count. Two more years of data would do more than any modelling change.
2. **Maintenance work orders.** Knowing what was replaced would separate "repaired" from "reset the counter" and explain cases like MCH-214.
3. **More sensor channels** - current draw, acoustic, oil analysis - to cover failure modes these two miss.
4. **Survival modelling.** With more events, a time-to-event model would use the censored preventive-maintenance cases that are currently dropped, and would give an expected time to failure rather than a fixed-window probability.
5. **Feed technician outcomes back.** Recording what each alert actually found turns the false-positive rate into a measured quantity and enables retraining on real operational labels.
6. **Per-line or per-asset-class thresholds**, once there are enough events per line to set them without overfitting.
