### Machines do not share an operating point

Median temperature by machine spans **56.3 to 69.9 degC** (a 13.6 degC spread), and median vibration spans **0.31 to 1.25 mm/s** (a 4.0x ratio).

A single fleet-wide threshold cannot work. MCH-213 normally runs at 56.3 degC while MCH-200 normally runs at 69.9 degC, so any global cut-off either fires constantly on MCH-200 or never fires on MCH-213. This is the direct justification for machine-relative features.

## 7. Maintenance events (run-hours resets)

`run_hours_since_maintenance` resets to 0 at each maintenance event. Two kinds of reset appear in the data:

1. **17 resets that coincide with `failure_event = 1`** - unplanned repairs.
2. **5 resets with no failure flag** - planned/preventive maintenance:

   - MCH-209 at 2026-03-05 01:00:00
   - MCH-210 at 2026-03-09 21:00:00
   - MCH-213 at 2026-03-10 06:00:00
   - MCH-201 at 2026-03-10 21:00:00
   - MCH-214 at 2026-03-11 02:00:00

In the 24 hours before those planned interventions, vibration sat a median **2.2 standard deviations** above the machine's own normal while temperature was only **0.4** above. In other words, preventive maintenance was carried out on machines showing a vibration-only anomaly.

**Consequence for labelling:** we cannot know whether those machines *would* have failed. Calling those hours negatives would actively teach the model that rising vibration is harmless. They are therefore treated as censored and excluded from training and evaluation - see `app/ml/labeling.py`.

### Recovery after the event

One hour after a failure, temperature returns to -0.19 SD and vibration to -1.04 SD - i.e. the repair restores the machine to normal immediately. Rows after a failure are therefore ordinary negatives, but the failure hour itself is excluded (the machine is already down, which is an observation rather than a prediction).

## 9. Data-quality findings and what was done

| Finding | Extent | Treatment |

| Duplicate `(machine_id, timestamp)` rows | 10 rows, all on MCH-200, identical values | Dropped, keeping the first occurrence |
| Missing temperature | 648 (1.49%), scattered across all established machines | Linear interpolation within a machine, limited to 3-hour gaps, with a `temp_imputed` flag kept as a model feature |
| Missing vibration | 432 (1.00%) | Same treatment, with `vib_imputed` |
| One failure row has a missing temperature reading | MCH-201, 2026-04-20 00:00 | Interpolated like any other gap; that row is excluded from training anyway |
| Extreme class imbalance | 17 positive events in 43,344 rows | Drives the whole evaluation design: PR-AUC and episode-level recall rather than accuracy, F2 threshold selection, chronological validation |
| Censored preventive-maintenance events | 5 interventions | Pre-intervention hours excluded from training and evaluation |
| Timestamp continuity | No gaps; every machine is hourly and complete | Verified in `tests/test_data.py` |
| Sensor ranges | All values physically plausible; no negatives or impossible spikes | No clipping applied |

### Not found

- No machine identifier inconsistencies (all match `MCH-\d{3}`).
- No negative run-hours, and resets only ever go to exactly 0.
